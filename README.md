# Luma Event Camera PWA

Luma is a single application containing the Vite PWA and its local Express API. The
`server/` directory in this project is the API source; the outer `server/` directory
is legacy local-development material and is not part of the deployed application.

## Environment Variables

Create a `.env` file in the root of the `/luma` directory:

```env
# App mode: 'local' or 'production'
VITE_APP_MODE=local

# Leave empty to use Vite's same-origin API proxy locally and the same Vercel domain
# in production.
VITE_API_BASE_URL=

# Local Express API
DATABASE_URL=postgresql://postgres:YOUR_PASSWORD@localhost:5432/madetogether
PORT=3000
UPLOAD_DIR=./uploads
USE_HTTPS=false
```

## Local Development

### Standard Development

```bash
npm install
npm run dev:all
```

The PWA is available at `https://localhost:5173` and the API at
`http://localhost:3000`. Vite proxies `/api` and `/uploads` to the local API.

Run `npm run db:migrate` before the API for a new database. Use `npm run dev` or
`npm run dev:server` when only one process is needed.

## Seating plan

From an event card on **My Events** (`/host`), open **Manage invitation** beneath
**View Dashboard**. This opens the
website builder; the invitation sidebar switches between **Website**, **Guest
list**, and **Seating plan** for the same event. On phones, open the menu at the
top to access these sections. Draft website edits are saved before leaving
the builder, including when using Back; if saving fails, the builder stays
open with a retry option.

The builder offers three invitation looks: **Photo Letter** (botanical and
photo-forward), **City Vow** (bold editorial), and **Sunday Heirloom** (warm
and classic). Selection cards show each look; the live preview uses the same
layout as the published invitation. Cover photos, palette, and heading style
remain editable after choosing a look. Each template includes entrance and
scroll motion, with ambient details where appropriate; motion is disabled
when the visitor requests reduced motion.
The preview shows the current draft; publish again after edits to update the
public invitation. The RSVP search button uses the editor's Button label in
both views, and the closing message stays visible at the end of the page.
Every invitation ends with a madeTogether copyright footer, even when the
optional closing section is hidden. Host pages, including invitation management
and the event dashboard, use the same compact copyright footer below their
content.

On a published invitation, a circular section menu appears at the bottom right
after the opening section scrolls out of view. It links to the published,
visible sections and **Back to top**; the editor preview does not show this
menu.

Invitation URLs begin with the event's unique ID, followed by an editable title;
republishing an older invitation changes its previous URL, so share the new link.
The **Shared link preview** fields in the website editor set a separate title,
description, and image for the card shown when the published URL is shared.
Blank fields use the invitation names, message, and cover photo. Changes to the
shared card go live only after publishing again. Messaging apps may cache a
previous card and need time or their link debugger to refresh it.

In **Seating plan**, create tables with a seat
count, search the unassigned guest roster, and choose a table for each guest.
Guests may be moved or unassigned; removing a table leaves its guests unassigned.
If a table exceeds its seat count, the plan warns you but permits the assignment.
Use **Add and seat a guest** to create a guest-list entry and place them at a table
in one step, with an optional existing invitation group. The roster's total
counts each guest once.
Invitation-management success and error messages appear as dismissible,
upper-right notifications across the website editor, guest list, and seating plan.
When adding a guest to a group, the individual named-additional-guest and
additional-guest-allowance fields are hidden; use the group allowance instead.
The guest-list overview highlights confirmed attendees first as the food
headcount. It counts every person on the roster, including additional
guests, and separately shows how many have responded,
or are still awaiting a response. Each group member is counted individually;
the RSVP Party total is not repeated in each guest's table row.

Attending RSVP companions and previously unlisted named group attendees appear
in the guest list automatically. The guest list's RSVP relationship column
shows their invitation origin and proxy role without friend numbers; autogenerated
guest names still use friend numbers. The public search list shows only the invitation
holder's name, even when a named additional guest matches the search. The
RSVP modal highlights the total reserved seats; guests first respond for
themselves, then respond for every reserved additional seat. Additional guests
can be marked **Attend all** or **Decline all** at the top of the second step.
For a family invitation, add each named member to the group and mark one or
two of them as **RSVP responder** in the guest list. Public RSVP search accepts
the group name or a responder's name, but not the name of a non-responder.
Selecting the group shows every member on the second step, where the responder
can set each person's attendance or use **Attend all** or **Decline all**.
The host can change responders by editing guests; additional-guest allowances
for groups remain available through private RSVP links.
Additional guests
show the invitation's response date in the roster when their attendance is
submitted. Host-named guests consume their reserved seats; unnamed seats can
be named or left as
“Guest name friend #N.” All reserved seats remain on the host roster with
their own attending, declined, or undecided status. If the invited guest
selects “Not attending,” a confirmation offers a proxy choice or declines
all additional seats. If an additional guest attends, the invited guest must
choose an attending guest as their proxy; the roster labels that guest
“Proxy of [invited guest].”
Guests review their complete response before confirming. A saved RSVP then
shows a guest-list receipt with the invitation name, responses, submission
time, and reference, downloadable as a PDF generated entirely in the browser
(including on Android and iOS). Unlisted names instead receive a request
receipt clearly marked pending host review, not guest-list confirmation.
On the public invitation, RSVP search, submission, and receipt-download errors
appear in a dismissible upper-right notification; a failed submission keeps
the guest's answers so they can retry.
RSVP party totals include only attending guests; declined or undecided reserved
seats are removed from table assignments. Changing an RSVP
reconciles only guests created from that RSVP and their seating assignments.
Use **Print** for a
print-friendly plan or **Export CSV** for the current assignments and unassigned
guests. Run `npm run db:migrate` after updating an existing installation to add
the seating schema; opening the host guest list or seating plan reconciles
earlier responses.

## Vercel Deployment

Create one Vercel project with `luma` as its Root Directory. Vercel builds the PWA,
serves it from `dist`, and routes `/api/*` to `api/index.ts`, which exports the same
Express app used locally. Configure `DATABASE_URL` in Vercel environment variables.
Published invitation paths are also routed through this app to inject per-event
Open Graph and Twitter metadata into the HTML before sharing crawlers read it.

The current filesystem upload adapter is for local development only. Move uploads to
private object storage before production; Vercel function storage is not durable.

### Mobile Testing via LAN

For testing on a physical phone with camera access:

1. Start the dev server:
```bash
npm run dev
```

2. Find your PC's LAN IP address:
   - Windows: `ipconfig` (look for IPv4 Address)
   - Mac/Linux: `ifconfig` or `ip addr`

3. The dev server will show the LAN URL, e.g.:
   ```
   ➜  Local:   http://localhost:5173/
   ➜  Network: http://192.168.1.100:5173/
   ```

4. Access the app from your phone using the Network URL

5. Test event URL: `http://192.168.1.100:5173/e/demo`

### Camera Access on Mobile

Browser camera APIs require HTTPS in production. For local development:

**Option 1: Use the LAN URL directly (may work on some browsers)**
- Some browsers allow camera access on local network IPs

**Option 2: Use a local HTTPS certificate (recommended)**
- Set up a local SSL certificate for development
- Configure Vite to use HTTPS

**Option 3: Use a tunnel (quick testing)**
- Use ngrok, Cloudflare Tunnel, or similar
- Provides temporary HTTPS URL

## Testing the Flow

1. Visit `http://localhost:5173/e/demo` (or LAN URL on mobile)
2. You'll see the landing screen
3. Click "LET'S TAKE PHOTOS"
4. Enter your name
5. Grant camera permission
6. Take photos (10 shots available)
7. Each photo goes through: capture → developing → uploading → complete
8. After all shots or clicking "I'M DONE", leave an optional message
